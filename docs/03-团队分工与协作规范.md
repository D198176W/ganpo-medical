# 03 · 团队分工与协作规范

| 项 | 内容 |
|---|---|
| 团队规模 | 4–5 人 |
| 分工 | **前端组 ≈ 一半，后端组 ≈ 一半** |
| 工作方式 | 全员使用 AI 编码助手（每人的助手独立工作） |
| 项目根目录 | `D:\ideaAllCode\ganpo-medical\ganpo-medical` |
| 日期 | 2026-09-27 |

> ⚠️ **本文档的核心目的**：让 4–5 个并行的 AI 助手**不互相踩踏、不重复实现、产出风格一致**。
> 每人的助手在开始工作前，必须先读 `AGENTS.md` + `docs/00` + 本文档。

---

## 1. 为什么需要这份规范

本项目已由组长完成第一轮梳理（清除 46 处冲突、修复构建、清理 171 MB 冗余、配置外部化）。
但代码库中存在大量**历史包袱**，AI 助手在没有约束的情况下极易做出**看似合理但破坏架构**的改动：

| 风险 | 具体表现 |
|---|---|
| **重复实现** | `users` 表已被 3 个模块各自实现一次；新手易再加第 4 套 |
| **沿用错误模式** | 3 套响应体、3 套 JWT —— 助手容易照抄就近的那一套 |
| **误判「已实现」** | 后端有 **225 处整段注释代码**、36 处 `return null`、大量空壳方法 |
| **破坏构建** | 子模块 pom 写死版本、重复 import BOM、恢复已停用的类 |
| **并发冲突** | 两人同时改同一文件；前端硬编码后端地址 |

## 3. 目录所有权（**避免并发冲突的关键**）

**一个目录同一时间只由一个人（一个助手）负责。** 需要跨目录改动时，先在群里同步。

```
ganpo-medical/
├── pom.xml ...................... 后端 A 独有
├── AGENTS.md / docs/ ............ 组长维护（改动需报备）
├── .gitignore ................... 后端 A
├── scripts/ ..................... 后端 A
│
├── src/ ......................... 前端组
│   ├── router/ store/ utils/ .... 前端 A 独有
│   ├── views/ components/ ....... 前端 B（咨询/病理/紧急救助 由对应负责人）
│   └── assets/ .................. 前端 A
│
├── consult/ ..................... 后端 C
├── pathology/ ................... 后端 C
├── health-management/ ........... 后端 B
└── medical-resource/ ............ 后端 B
```

**共享文件变更规则**：

| 文件 | 谁能改 | 规则 |
|---|---|---|
| 根 `pom.xml` | **仅后端 A** | 其他人需要新依赖时，提交 issue 或群里说明，由后端 A 添加 |
| `.gitignore` | 仅后端 A | — |
| `AGENTS.md` | 仅组长 | — |
| `docs/*` | 各自负责的章节 | 新增文档需在群里说明 |
| `<模块>/AGENTS.md` | 该模块负责人 | — |

## 4. 分支与提交流程

### 4.1 分支策略

```
main                 ← 始终可构建；只接受通过验收的合并
 └── feature/xxx     ← 每人一条，命名规则见下
```

分支命名：

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feature/` | 新功能 | `feature/health-record-api` |
| `fix/` | 修 Bug | `fix/result-response-body` |
| `refactor/` | 重构 | `refactor/pom-unify-versions` |
| `docs/` | 文档 | `docs/module-guide` |

**规则**：
1. 每条分支**只做一件事**，避免巨型 PR
2. 合并前必须保证 `mvn clean package -DskipTests` 通过（后端）或 `npm run build` 通过（前端）
3. 合并前**先 rebase main**，解决冲突后再提 PR
4. **不要 force push 到 `main`**

### 4.2 提交信息规范

```
<类型>(<范围>): <简短描述>

示例：
feat(health): 新增健康记录分页查询接口
fix(consult): 修复号源查询工具返回假数据的问题
refactor(pom): 统一 MyBatis-Plus 版本至 3.5.7
docs(agents): 补充 pathology 模块的注意事项
```

类型：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`

### 4.3 回滚点

Git tag **`baseline-before-rescue`** 保存了本轮梳理之前的原始状态。需要对比或回退时可用：

```powershell
git diff baseline-before-rescue -- <文件路径>
git show baseline-before-rescue:<文件路径>
```

## 5. 后端协作约定

### 5.1 依赖管理（**最容易出错的地方**）

- **所有版本只在根 `pom.xml` 的 `<properties>` + `<dependencyManagement>` 中声明**
- 子模块的 `<dependency>` **不写 `<version>`**
- 子模块**不要**再 `import spring-boot-dependencies`（父工程已 import）
- **不要**在子模块重复声明 `maven-compiler-plugin` 的 `annotationProcessorPaths`
- 需要新依赖 → 告知后端 A 统一添加

### 5.2 响应体（Phase 3–4 后统一）

```json
{ "code": 0, "message": "成功", "data": { } }
```

**成功码 = 0。** 在统一之前：
- `medical-resource` 已是 `0` 语义 → 可参考
- `health-management` 是 `200` 语义 → **不要照抄**
- 新写接口请**先按 `0` 语义**，避免将来返工

### 5.3 配置与密钥

- 数据库、JWT、AI Key 一律 `${ENV_VAR:默认值}`
- **禁止**把真实口令/密钥写进任何受版本控制的文件
- `health-management` 的 `jwt.secret` 必须是**合法 Base64**（`JwtConfig` 会解码）

### 5.4 数据库

- 项目数据库为**专属实例 `:3307`**（搭建方式见 `docs/02` §4.1）
- 每个模块的表结构变更，**必须同步更新该模块的 `src/main/resources/db/schema-mysql.sql`**
- 建表脚本需**可重复执行**（用 `CREATE TABLE IF NOT EXISTS`）

### 5.5 注释与日志

- 注释**一律中文**
- 不要留 `System.out.println` 调试输出（历史上 `AuthController` 有一处，已清理）
- 用 Lombok `@Slf4j` + `log.info/debug`

## 6. 前端协作约定

### 6.1 API 调用

- **统一走 `src/utils/request.js`**，不要直接 `import axios`
- ⚠️ `request.js` 默认导出的是 **axios 实例本身**，正确用法是 `request.post(...)`
  **不存在** `request.axios.post(...)` —— `MedicalResources.vue` 就是这么写错的
- 后端地址统一由 `.env.development` 的 `VITE_APP_BASE_API` 提供，**禁止硬编码**
  （`MedicalConsult.vue` 硬编码了 `http://localhost:8080/xiaozhi`，需改掉）

### 6.2 状态管理

- **Pinia 是唯一数据源**，不要把状态散落在组件的 `ref` 里
- 现有问题：页面普遍绕过 store 直接读写 `localStorage` → 迁移时逐步收敛

### 6.3 样式

- 全局样式在 `src/assets/styles/global.css`（`main.js` 引入，**纯 CSS**）
- ⚠️ 项目里**没有真正启用 Tailwind**（`tailwindcss 4.1.14` 是死依赖，无 config、无 postcss 插件）
- ⚠️ 3 个紧急救助组件的 `<style>` 里有 `@apply`，因无插件处理而**静默失效** → 需改用真实 CSS
- 组件内联 `<style>` 占比 45–55%，**新代码请抽公共类**，不要继续堆内联样式

### 6.4 组件规模

现有超大单文件组件（改动需谨慎）：

| 文件 | 行数 |
|---|---|
| `views/PathologyService.vue` | 1992 |
| `views/EmergencyGuidelines.vue` | 1694 |
| `views/CommonIllnesses.vue` | 1565 |
| `views/MedicalResources.vue` | 1307 |
| `components/chat/MessageBubble.vue` | 1274 |
| `components/chat/ChatWindow.vue` | 1061 |
| `components/common/VoiceButton.vue` | 1054 |

**改这些文件时只改必要部分，不要顺手重构。**

让自己的助手先读：

```
1. AGENTS.md                          ← 铁律与全局约定
2. docs/00-项目现状与差距分析.md        ← 什么已完成 / 什么是空壳
3. docs/02-项目说明书.md               ← 自己负责模块的详解
4. docs/03-团队分工与协作规范.md（本文） ← 目录所有权与约定

### 7.2 助手提示词模板

```

铁律提醒：

3. 依赖版本只在根 pom.xml 声明，子模块不要写 <version>

- ❌ 不要新增第 4 套响应体 / JWT / User 实现
- ❌ 不要提交 `target/`、`node_modules/`、`dist/`、`.idea/`

## 8. 验收与联调

### 8.1 提交前自检清单

| 检查项 | 命令 / 方式 |
|---|---|
| 后端能构建 | `mvn clean package -DskipTests` |
| 无冲突标记残留 | PowerShell 扫 `^<<<<<<< `（**不要用 grep 工具**，它在本仓库会漏检） |
| 无硬编码密钥 | 扫 `password:`、`secret:`、`sk-` |
| 前端能构建 | `npm run build` |
| 只改了自己负责的文件 | `git status` |

### 8.2 联调顺序

1. **后端契约先定**：接口路径 + 请求/响应结构，写进 `docs/02` 或模块 `AGENTS.md`
2. 后端提供 **knife4j / `.http` 脚本**，前端可先行 mock
3. 前端接 `vite.config.js` 的 `server.proxy`，不直连各服务端口
4. 联调时**先起数据库（3307）**，再起服务

### 8.3 每周同步

- 每人同步：本周完成 / 下周计划 / **阻塞点**
- 阻塞点优先解决**跨组依赖**（如前端等后端的接口契约）

## 10. 沟通与文档维护

- **改动约定后，必须同步更新对应文档**（否则下一个人的助手会按旧约定工作）
- 新增模块 → 新增 `<模块>/AGENTS.md`，并在根 `AGENTS.md` §3 目录地图与 §10 索引中登记
- 发现文档与代码不一致 → **以代码为准，并修正文档**
- 不确定的地方**问，不要猜**；本项目历史上有过多处「看起来对其实错」的坑
