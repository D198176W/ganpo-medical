### 1.1 模块职责与依赖规则

| 模块 | 职责 | 依赖谁 | 谁依赖它 |
|---|---|---|---|
| `ganpo-common` | 统一响应体、分页、错误码、业务异常、JWT 工具、用户上下文、常量 | 仅 jackson / jjwt | **全部模块** |
| `ganpo-common-web` | 全局异常处理、用户上下文拦截器、自动装配 | `ganpo-common` + `starter-web` | 所有 **Servlet** 服务 |
| `ganpo-api` | 跨服务 DTO 契约 + OpenFeign 客户端 + fallback | `ganpo-common` + `openfeign` + validation | 需要调其他服务的服务 |
| `ganpo-gateway` | 路由、统一鉴权、CORS、限流 | **仅 `ganpo-common`** | 前端 |
| 业务服务 | 各自领域逻辑 | `common` + `common-web`（+ `api`） | 网关 / 彼此（经 Feign） |

> 🔴 **必须遵守**：`ganpo-common` **不得引入 `spring-boot-starter-web`**。Spring Cloud Gateway 是 **WebFlux 响应式**，若 common 带 servlet 依赖，**网关会因栈冲突启动失败**。servlet 相关一律放 `ganpo-common-web`。

## 3. 技术选型与落点（后端 / 架构）

| # | 技术 | 业务落点 | 可量化目标（写简历用） |
|---|---|---|---|
| 1 | **Spring Cloud Alibaba 2023.0.1.0**<br>Spring Boot 3.2.4 | 微服务基础框架 | 版本矩阵与官方表精确匹配 |
| 2 | **Nacos 2.3.2** | 注册中心（服务自动上下线）+ 配置中心（配置热更新） | 实例上下线网关自动感知；改配置免重启 |
| 3 | **Spring Cloud Gateway** | 统一入口、统一鉴权、CORS、路由 | 前端只连 1 个端口；鉴权收敛到 1 处 |
| 4 | **OpenFeign + LoadBalancer** | `consult → resource`（预约/号源）、各服务 `→ auth`（用户） | **消除 3 套重复 User 表与 3 套 JWT** |
| 5 | **Redis** | ① 缓存医院/科室/知识库热点<br>② **Redisson 分布式锁**防重复预约<br>③ JWT 黑名单（登出立即失效）<br>④ 验证码存储 | 热点查询 P95 从 ~320ms → ~45ms；<br>并发重复预约 **0 例** |
| 6 | **Sentinel** | ① 网关路由级限流 ② **Feign 熔断降级** ③ 热点参数限流 | 下游故障时自动降级，接口不雪崩 |
| 7 | **Seata（AT 模式）** | 预约挂号跨服务一致性：`resource` 扣号源 + `health` 写「就医计划」 | 第二步抛异常时，两侧数据**均回滚** |
| 8 | **RocketMQ** | ① 预约成功 → 异步通知 ② 健康提醒扫描 → 推送 ③ 报告生成异步化 | 预约接口响应时间显著下降 |
| 9 | **Elasticsearch** | 医院 / 科室 / **病理知识库**全文检索 + 高亮 | 从 `LIKE` 全表扫描 → **毫秒级**；中文分词生效 |
| 10 | **Nginx** | 前端静态资源 + 网关负载均衡（upstream 多实例） | 静态资源与 API 同源，免 CORS |
| 11 | **Docker Compose** | 全部服务 + 中间件编排，**按 profile 分阶段** | 全新环境 30 分钟一键起 |
| 12 | **SkyWalking** | Java Agent 全链路追踪、服务拓扑、慢 SQL 定位 | 可视化调用链与瓶颈定位 |

## 7. 关键接口契约（`ganpo-api`）

```
com.ganpo.api.dto
    UserDTO               id / username / realName / phone / role
    HospitalDTO           id / name / level / address / lat / lng / coreDepartments
    DepartmentDTO         id / name / parentId / alias
    AppointmentDTO        id / userId / hospitalId / departmentId / doctorId /
                          date / timeslot / status / ticketNumber
    SlotQueryDTO          hospitalId / departmentId / date / timeslot / doctorName
    SlotQueryResult       available / remaining / doctorName

com.ganpo.api.client
    AuthClient      @FeignClient("ganpo-auth")       getUserById / getByUsername
    ResourceClient  @FeignClient("ganpo-resource")   createAppointment / cancelAppointment /
                                                     getAppointment / querySlots /
                                                     getHospital / listDepartments
    NotifyClient    @FeignClient("ganpo-notify")
    （各 Client 配 Sentinel fallback 工厂）
```

### 7.1 契约的来源依据（非臆造）

| 证据 | 结论 |
|---|---|
| `consult/tools/AppoinmentTools.java` 直接操作**自己的** `appointment` 表（`bookAppointment`/`cancelAppointment`） | 预约归 **`ganpo-resource`** 独有；consult 删除自身 entity/service/mapper |
| `queryDepartment()` 只 `System.out.println` 后 `return true`（**假实现**） | 改为真实 Feign 调用 → **真实业务缺口被填上** |
| `medical-resource` `/api/appointments` 模型更完整（含 `ticketNumber`/`timeslot`/`status`） | resource 是预约**权威服务** |
| 三套 `User` 实体字段各异（`password_hash` / `name,phone` / `role,institution,doctor_name`） | 合并为 `ganpo-auth` **单一 `users` 表**（字段并集 + `role`） |
| `hospitals` 同时被 health-management 与 medical-resource 映射 | 归 resource（模型更丰富），health 删除 |

## 8. 统一约定

### 8.1 响应体

```json
{ "code": 0, "message": "成功", "data": { } }
```

- **成功码 = 0**（前端 `utils/request.js` 已按 `code === 0` 判定；`medical-resource` 也已是 `0` 语义）
- 废弃 `health-management` 的 `200` 语义
- `consult` 的流式接口不包装（保持 SSE）

### 8.2 鉴权链路

```
登录  →  ganpo-auth 签发 JWT
请求  →  Nginx  →  Gateway 校验 JWT  →  注入 X-User-Id / X-User-Roles  →  下游服务
下游  →  UserContextInterceptor 读取请求头  →  写入 UserContext(ThreadLocal)
```

- 下游服务**不再各自解析 token**（消除 3 套 `JwtUtil`）
- JWT 必须包含 `authorities` claim（否则 `health-management` 现有过滤器会 NPE）
- 登出 → token 进 Redis 黑名单，立即失效

### 8.3 数据库

| 阶段 | 状态 |
|---|---|
| 初期 | `health_management` / `pathology` / `medical_resource` / `guiguxiaozhi` 四库（与原模块对应，端口 3307） |
| Phase 6 后 | 三套 `users` 合并为 `ganpo-auth` 的**单一 `users` 表** |
| Phase 8 后 | `consult` 的 `appointment` 表**废弃**（预约归 resource） |

## 9. 简历呈现建议

### 9.1 推荐写法（技术 + 数据）

> **赣鄱医枢 · 区域智能医疗服务平台**（团队项目 · 后端负责人）
> - 基于 **Spring Cloud Alibaba 2023** 构建微服务架构（Nacos 注册配置中心 + Gateway 网关 + OpenFeign 服务调用），拆分认证、健康、问诊、病理、资源、通知 6 个业务服务
> - 设计 `common` / `common-web` / `api` 三层复用结构，统一响应体与鉴权链路，**消除原有 3 套重复的用户认证实现**
> - 引入 **Redis 缓存 + Redisson 分布式锁**解决预约并发重复提交，热点查询 P95 **从 320ms 降至 45ms**
> - 使用 **Sentinel** 实现网关限流与 Feign 熔断降级；**Seata AT** 保障「扣号源 + 建就医计划」跨服务一致性
> - 基于 **LangChain4j** 构建医疗问答 Agent（RAG + Function Calling），融合 **Elasticsearch 关键词检索与 Milvus 向量检索**提升召回；接入 **Qwen-VL** 实现病理切片多模态识别
> - 以 **Docker Compose** 编排全栈环境，**SkyWalking** 做全链路追踪

### 9.2 诚实提醒

1. **只列 8–10 个能讲透的**。19 个技术全写上去，面试官一定会挑最深的几个追问。
2. **每个技术都要能回答「为什么用它、不用会怎样、你踩了什么坑」**。
3. **数字比技术名词更有说服力**。上文的 `320ms → 45ms`、`0 例重复预约` 这类结论，在 Phase 2/4 阶段就要**实测记录下来**，否则答辩时无法复现。
4. **面试高频追问预判**：
   - 「为什么用微服务？这个体量用单体不是更简单？」→ 答案要落在**领域边界**（AI 与业务算力特性差异大、病理图像处理独立扩展）与**团队并行开发**上，而不是「显得高级」
   - 「Seata 解决的是什么问题？不用会怎样？」→ 必须能说清**具体哪两个写操作跨了服务**
   - 「ES 和 Milvus 都做检索，区别是什么？为什么两个都要？」→ 关键词精确匹配 vs 语义相似召回

## 10. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| **16 GB 内存 + C 盘 28.7 GB** | 中间件跑不动、Docker 拉不动镜像 | Compose profiles 分阶段；Docker 数据盘迁 D；演示分场景录制 |
| 微服务化周期长（~34 周单人） | 中途无可用演示 | **Phase 5 即为可提交里程碑**；团队并行压缩到 ~14–18 周 |
| 技术栈过大，团队吃不透 | 答辩被问穿 | 每项必须有真实落点与量化数据；按 §9.1 精选简历条目 |
| Seata 找不到真实跨服务写场景 | 沦为"为简历硬塞" | 已设计落点（扣号源 + 写就医计划）；若场景不成立则砍掉 |
| **Nacos 在 JDK 21 上有反射限制** | 注册中心起不来 | **用 `D:\JDk11` 启动 Nacos**（已验证本机存在）；备用 `--add-opens` 参数 |
| 合并三套 User 导致数据模型冲突 | `ganpo-auth` 返工 | **先写数据库设计文档再动代码**；字段取并集 + `role` 区分 |
| `health_management`/`consult` 表结构靠实体反推 | 与真实库不符 | 见 `00` 文档 §8 待确认清单 |
| Milvus 与 ES 不可同开于 16 GB | 混合检索无法现场演示 | 二选一现场演示，另一项录视频 |
